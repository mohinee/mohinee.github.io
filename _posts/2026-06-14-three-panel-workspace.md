Most developer tools with a split-pane interface treat the panels as UI concerns. They decide how wide each pane is, how to handle resizing, how to theme them consistently. The underlying application is one thing. The panes are windows into it.

The Genesis workspace — three panels: chat/conversation, Monaco code editor, and live preview — was designed differently. The panels are not three views of one application. They are three independent failure domains that happen to share a screen.

This is not a subtle distinction. It determined the entire security model, the error handling strategy, and the failure behavior of the system.

---

## What the Three Panels Are

**Panel 1: Chat** — The conversation interface between the user and the agent pipeline. The user describes what they want to build. The agents respond with questions, status updates, and progress signals. This panel is the command layer. It is fully trusted. It runs in the main Vue application context.

**Panel 2: Code Editor** — A Monaco editor instance displaying the current contents of the generated files. It is read/write: the user can inspect and edit generated code before it's previewed or executed. This panel is semi-trusted. The content is generated by AI and should be treated as potentially incorrect, but it isn't running — it's just text.

**Panel 3: Live Preview** — An iframe rendering the generated application. The user sees the output of what the agents built. This panel is **explicitly untrusted** and isolated accordingly.

---

## The iframe Security Decision

The live preview runs in a sandboxed iframe. The sandbox attribute configuration is not arbitrary:

```html
<iframe
  sandbox="allow-scripts"
  srcdoc="..."
/>
```

Two things to notice:

**`allow-scripts` is present.** Generated applications need JavaScript to run. Without this, the preview would render only static HTML.

**`allow-same-origin` is absent.** This is the critical decision. When `allow-same-origin` is omitted, the iframe is treated as a cross-origin document regardless of what domain it's actually served from. This means it cannot access the parent window's DOM, cannot read cookies from the parent origin, cannot access localStorage, and cannot make credentialed requests using the user's session.

The consequence: if the generated code contains malicious JavaScript — whether injected by a compromised model, a prompt injection attack, or a coding error that happens to produce dangerous behavior — it cannot escalate into the parent application. It cannot steal the user's authentication tokens. It cannot modify the conversation history. It cannot exfiltrate data to an external endpoint using the user's session credentials.

It is contained. It can only hurt itself.

## Independent Failure Domains

The deeper architectural principle is that the three panels should fail independently.

If the live preview crashes — the generated application throws an unhandled exception, enters an infinite loop, or renders nothing — the chat panel and code editor should continue working normally. The user should be able to see the error, edit the code to fix it, and regenerate the preview without losing conversation history or pipeline state.

If the agent pipeline gets into an error state and stops responding — a timeout, a rate limit, an ambiguous instruction that causes the pipeline to halt — the code editor should still be readable and editable. The last successful output should be intact.

If the code editor loses state somehow — a network partition, a synchronization failure between the editor and Firestore — the conversation history should be recoverable independently, because it's stored in a separate Firestore collection, not derived from editor state.

This is the same principle as bulkheads in a ship: when one compartment floods, the others stay dry. You design for failure isolation, not just failure prevention.

---

## The Contract Between Panels

Independent failure domains create a coordination problem: how do panels communicate when they need to?

The panels communicate through defined contracts, not direct references.

The chat panel does not directly mutate the code editor's content. It writes to Firestore. The code editor subscribes to Firestore updates and reflects the current file state. If the chat panel's write fails, the editor doesn't get a partial or corrupt update — it simply doesn't update until the write succeeds.

The code editor does not directly push to the preview iframe. When the user triggers a preview, the current editor content is serialized, passed through a Cloud Function that validates it, and rendered into the iframe's `srcdoc`. The validation step — checking that the content is well-formed HTML/JS before rendering — means malformed output doesn't crash the preview in unpredictable ways.

The preview iframe cannot write back to either panel. There is no callback from preview to chat or editor. This is intentional. The preview is read-only output. If the user wants to act on what they see in the preview, they do it through the chat panel.

This directional data flow — chat → editor → preview, no reversal — is what makes the failure isolation tractable. You can reason about what each component can and cannot affect.

## Why Monaco, and What That Costs

The code editor is Monaco — the same editor that powers VS Code. The choice was driven by one feature: document model isolation.

Monaco maintains its own document model separate from the DOM. When you update editor content, you're calling Monaco's API, not writing to the DOM directly. This matters for AI-generated content: when the agent pipeline writes several hundred lines of code, Monaco's incremental update model means the editor doesn't re-render from scratch. It applies the delta. For large files or rapid updates (streaming code generation), this is the difference between a usable interface and a janky one.

The cost is bundle size. Monaco is not small. For a single-page app, the payload cost is real. The decision was correct for Genesis because the editor is a primary surface, used for most of the session. For a tool where code inspection is incidental, a lighter editor would be appropriate.

---

## Streaming and the Editor

The agent pipeline streams output via Server-Sent Events. As the Developer agent writes code, the output streams into the editor in real time rather than appearing all at once after the agent finishes.

This creates a specific problem: how do you handle an editor whose content is being written by a stream while the user might also be editing it?

Genesis resolves this with a simple rule: while a pipeline pass is active, the editor is read-only. The stream writes. When the pipeline completes, the editor becomes read-write. The user can then edit, override, or redirect the next pipeline pass via the chat panel.

This is not a sophisticated conflict resolution strategy. It's a constraint that eliminates the conflict. When you can't resolve a problem elegantly, sometimes the right move is to make the problem not exist.

---

## What This Looks Like in Practice

A typical session:

1. User types a feature request in the chat panel.
2. The Planner and Architect passes run; the chat panel shows progress signals.
3. The Developer pass begins; code streams into the editor in real time, which is locked to read-only.
4. Developer pass completes; Tester and Reviewer passes run in the background.
5. If the Reviewer approves: editor becomes editable, preview refreshes with the new code.
6. If the Reviewer blocks: chat panel shows the critical issues, editor remains editable, user can modify and re-trigger.

At no point during this flow does a failure in one panel cascade into another. The preview crashing on step 5 doesn't interrupt the step-6 chat notification. The chat panel losing its SSE connection during step 2 doesn't corrupt the pipeline state — the agents are writing to Firestore, not to the SSE stream.

---

## The Design Principle

Splitting a UI into panels is easy. Designing those panels as independent failure domains — with explicit contracts between them, directional data flow, and trust levels enforced at the boundary — requires treating the UI as an architecture problem, not a layout problem.

The preview iframe sandbox attribute is a one-line configuration change. The reasoning behind it — that AI-generated code is untrusted and must be contained — is an architectural stance that shapes everything downstream.

The most important UI decisions in Genesis are not about fonts or colors or responsive breakpoints. They're about where trust boundaries live and what happens when things fail.
